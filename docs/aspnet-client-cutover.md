# ASP.NET client cutover

The ASP.NET backend implements the application API route families, including hosted tutor actions. Next.js remains the web frontend and provides the browser's same-origin API proxy. Set `RECALL_API_URL` to route browser API and auth traffic to ASP.NET; native and Electron clients use their configured API origin directly. Production use still requires the corresponding Supabase, provider, storage, rate-limit and trusted-proxy configuration described below.

## Client request paths

| Client      | How it reaches the API                                                                                               | Setting and current use                                                                                                                                                                                                                                                                           |
| ----------- | -------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Browser web | Same-origin `fetch`; session calls use HttpOnly Supabase SSR cookies                                                 | Next.js `proxy.ts` forwards `/api/*` and `/auth/*` when `RECALL_API_URL` is set. The example points to local ASP.NET at `http://localhost:5000`. Cookie auth, confirmation redirects and sign-out stay same-origin.                                                                               |
| Electron    | Main process reads Supabase session from encrypted storage and sends bearer tokens; renderer uses the preload bridge | `RECALL_API_URL` is the main process's direct whole API origin. Local example points directly to ASP.NET; production can use an API gateway or the ASP.NET origin. Desktop email confirmation is handled by its `recall://` callback through Supabase Auth, not the web `/auth/confirm` endpoint. |
| Expo native | Supabase Auth SDK stores session in SecureStore; API requests send bearer tokens                                     | `EXPO_PUBLIC_RECALL_API_URL` is a direct whole API origin. Local development can point to ASP.NET; production EAS releases require a reachable HTTPS origin. Native email confirmation calls Supabase Auth directly via `recall://auth/confirm`.                                                  |

For local API work, start ASP.NET on `http://localhost:5000` with `dotnet run --project backend/Recall.Api --urls http://localhost:5000`. Set `RECALL_API_URL=http://localhost:5000` in `apps/web/.env.local` and run the Next.js frontend; its proxy forwards browser calls while keeping them same-origin. No separate browser reverse proxy is needed in local development. Electron uses that value as its whole API origin and calls ASP.NET directly. Expo can use `EXPO_PUBLIC_RECALL_API_URL=http://localhost:5000` from a desktop-hosted simulator; for a physical device, use the development machine's LAN address and ensure ASP.NET listens on a reachable interface. Neither native setting redirects browser traffic. The backend has no permissive CORS policy; the web path avoids cross-origin browser requests and native HTTP clients do not enforce browser CORS.

The API reads server configuration from its own environment. It does not load `apps/web/.env` automatically. See [backend setup](../backend/README.md) for required Supabase settings and the handling of server-only secrets.

## Implemented route families

Current ASP.NET route mappings cover health; Supabase session, email confirmation, sign-out and OpenAI sign-in; account export and deletion; workspace snapshot reads and writes, review identity lookup, tombstones, review sync and private media; publication creation, public/unlisted reads, discovery updates, forks, share-token operations and published media; tutor session reads and all supported tutor actions, proposal resolution, privacy and retention; and the internal tutor-retention handler. The [migration inventory](aspnet-migration-inventory.md), [contract bridge](dotnet-contract-bridge.md), and [sync checklist](aspnet-sync-port-checklist.md) describe route behavior and compatibility boundaries.

The API calls found in the current web, Electron and Expo clients map to ASP.NET routes. Web calls use the workspace/sync/media, publication/media, account, tutor/privacy, tutor action, session/capabilities and browser auth route families above. Electron's allow-listed API transport uses bearer auth for workspace/sync/media, publication, account and tutor operations; its magic-link callback and sign-out use its local Supabase SDK session. Expo uses bearer auth for workspace/sync/media, publication, account and tutor operations, while magic-link issue and verification use Supabase Auth directly. Web passwordless sign-in also starts through the Supabase browser SDK; ASP.NET owns the web confirmation and session-cookie boundary. No current app API route was found without an ASP.NET method/path mapping. Supabase SDK calls are provider integrations, not Recall API routes.

## Routing and release sequence

1. Run the backend locally with the same Supabase schema, policies, RPCs and server-only feature configuration expected in deployment. Check `/health`, then exercise authenticated and unauthenticated paths with a development account. `backend/README.md` contains the .NET 10 setup and local Next.js proxy commands.
2. For browser deployment through Next.js, set the Next.js server's `RECALL_API_URL` to the ASP.NET origin. Its proxy forwards `/api/*` and `/auth/*`, including the `/api/internal/tutor-retention` job route; the backend implements the application route inventory. If ingress does the forwarding, route those paths to ASP.NET there and leave `RECALL_API_URL` unset to avoid a second proxy hop. Do not point the Next.js proxy back at its own public origin.
3. Keep browser traffic same-origin. The API enforces origin checks on sign-out and account deletion and issues secure session cookies in production; forwarding must preserve the original host and scheme and must not cache authenticated responses. Set `RECALL_TRUSTED_PROXY_IPS` to the API's exact proxy peer IP addresses so ASP.NET accepts forwarded host and scheme headers. Restrict direct API access to trusted ingress and configure the rate-limit IP header to be overwritten by that ingress.
4. Native and Electron clients call their configured API origin directly with bearer tokens. Set Electron's `RECALL_API_URL` and Expo's `EXPO_PUBLIC_RECALL_API_URL` to the ASP.NET origin or an API gateway that serves all routes. Release builds must use a reachable HTTPS origin. Native email confirmation uses the registered `recall://auth/confirm` callback and talks to Supabase Auth directly; it does not need ASP.NET `/auth/confirm`.
5. Keep Next.js handlers available as a rollback: unset `RECALL_API_URL` to serve API and auth requests through the existing Next.js handlers. Do not dual-write mutations. Preserve owner checks, idempotency, error schemas, offline recovery and retry behavior described in the inventory.

Before production activation, verify the deployed Supabase policies and RPCs, proxy trust and server-only secrets against [backend setup](../backend/README.md). Configure the retention scheduler with the ASP.NET origin and its expected secret if transcript cleanup is enabled.
