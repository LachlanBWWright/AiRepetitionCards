# ASP.NET migration inventory

This document inventories the Next.js route handlers now served by the ASP.NET Core API and records the expected wire behavior used for compatibility review. The Next.js handlers remain available as frontend-side fallbacks when `RECALL_API_URL` is unset. The inventory is based on handlers under `apps/web/src/app/**/route.ts` and contract and behavior notes in `docs/http-operations.md`, `docs/sync-protocol.md`, `docs/publishing-http.md`, `docs/published-media.md`, `docs/tutor-privacy.md`, and `docs/sign-in-with-chatgpt.md`.

## Migration risks and compatibility requirements

- **Cookie lifecycle is part of the backend contract.** Session status, email confirmation, sign-out, OpenAI OAuth start/callback, cookie flags, redirects and CSRF/origin checks must move together. Browser identity is a canonical Supabase session; provider identity tokens are not application credentials.
- **The API is used by three client families.** Web sends Supabase cookies; native and Electron use bearer credentials. Electron also uses a narrow API proxy. Preserve paths, methods, status/error envelopes, cache headers and the validated `x-recall-workspace-owner` checkpoint unless clients migrate in lockstep.
- **Supabase is also the authorization boundary.** Existing handlers use authenticated Supabase clients, owner filters and existing SQL/storage behavior. A privileged Postgres connection or service-role client can bypass row-level security. Keep service credentials limited to explicit account/privacy/retention tasks and prove equivalent owner checks before changing persistence access.
- **Sync correctness spans endpoint and local state.** Preserve append-only review history, causal order, cursor pagination, idempotent operation handling, tombstones, content hashes and partial checkpoints. Scheduling is rebuilt by clients from history; no server-side schedule should become authoritative.
- **Publishing capabilities are security-sensitive.** Share tokens authorize exact versions; token hashes, visibility, source lineage, content hashes, media integrity, replay recovery and public-only update discovery are all enforced in handler/application code. Do not treat an ordinary bearer account token as a share capability.
- **Rate limits and abuse controls are behavioral contracts.** Existing account/operation buckets, anonymous-publication limits, trusted-proxy IP hashing, retry headers, request/body/media limits and fail-closed store errors are documented in `docs/http-operations.md`. They must be represented in ASP.NET middleware/adapters with the same scopes and outcomes.
- **Tutor operations combine persistence, AI and privacy.** Keep output validation, user approval, quota accounting, durable budget/rate-limit behavior and retention semantics. Tutor-history deletion is independent of approved cards and review history.
- **OAuth and cleanup depend on durable external stores.** OpenAI website sign-in uses one-time PKCE transactions and durable identity mappings; account deletion must clean mappings before deleting the canonical account. Retention has two independent scheduler secrets and bounded, retry-safe deletion.
- **Request/response schemas are distributed.** `@recall/contracts` and domain schemas are authoritative for most envelopes, while several routes define private storage row schemas and validation inline. Cross-language compatibility fixtures should include success and expected-error payloads, duplicate/retry cases, hashes, identifiers and timestamps.

## Contract source map

The primary sources are `packages/contracts/src/index.ts` and the contract modules it exports, domain schemas under `packages/domain/src`, plus route-local schemas in the handler files. Feature behavior is documented in the files linked in the introduction; those docs describe client expectations and operational constraints but should be read alongside executable schemas and handlers when porting an endpoint.
