# Workspace and review synchronization

Hosted sync uses Supabase's canonical authenticated user. Web supplies cookies; native and Electron adapters supply bearer credentials. Application coordination lives in `packages/application/src/workspace-sync.ts`, with transports and storage composed by each client.

## Account ownership

The private local workspace persists a canonical UUID `syncOwnerId`. The authenticated server snapshot includes its verified `ownerId`; the coordinator compares identities before uploading content, attachments, reviews or tombstones. A fresh local workspace binds through a required durable platform checkpoint before preparing its outbox or making cloud writes. Failed binding persistence stops synchronization. The checkpoint reads the latest local workspace and retains edits made while the account lookup was pending.

Sign-out retains the offline workspace, its owner and append-only history. Signing in with a different account blocks synchronization and offers offline study/export or an explicitly separate fresh workspace after device reset. It never relabels the previous owner's workspace or copies its identifiers into the new account. Older unbound workspaces that contain a nonzero remote cursor, active remote backlog, content hashes, server conflicts, acknowledged tombstones or accepted sequenced reviews require an explicit confirmation that the data belongs to the signed-in account; declining preserves offline access and export. A device ID, zero cursor, false backlog flag and pending local reviews alone do not require legacy adoption.

Browser snapshot replacement checks the persisted account binding inside the IndexedDB write transaction. A stale tab or backup cannot drop or replace that binding; the write fails and the page preserves its current data in memory. Export unsaved content before reloading the latest durable workspace. Explicit device clearing uses the cross-tab erasure fence before a fresh workspace can bind to another account.

Every sync request after ownership discovery carries `x-recall-workspace-owner`; the first read also includes it when the client already has a verified account identity. Private media uses a gateway composed for that same owner. The server rejects a header/account mismatch before returning an authenticated mutation context. This prevents a cookie or desktop-session switch between asynchronous requests from uploading the old account's data under new credentials. Clients also invalidate pending receipts and conflict previews when canonical authentication changes. Reconciliation and explicit conflict acceptance check the saved owner again. Account IDs are compared canonically; email and display labels never establish ownership.

## Operation order

1. Read `/api/v1/workspace` to obtain the verified canonical owner, owner-scoped content snapshots, content hashes and area tombstones. Verify/adopt ownership and persist the binding through the platform checkpoint before any cloud write.
2. Prepare device identity, review sequences and the pending outbox from the latest durably bound workspace without dropping review history.
3. Upload verified media before content references it. Submit `/api/v1/workspace` with each existing area's base hash. A concurrent content edit produces a conflict preview; the client retains its copy until the learner explicitly accepts the server version.
4. Push at most 100 pending reviews in causal order to `/api/v1/sync`. Accepted IDs are acknowledged; the remaining outbox is retained for the next invocation. Card tombstones whose cards still have pending reviews are deferred. Push area tombstones to `/api/v1/workspace/area-tombstones` with the expected content hash only after pending reviews are accepted.
5. Pull `/api/v1/sync?cursor=...` in bounded pages. Validate every event/tombstone and increasing server sequence before applying it. Each invocation reads at most 100 pages; a larger backlog returns a successful partial checkpoint.
6. Reconcile against the latest local workspace, rebuild schedules from merged append-only events, update content hashes/cursor and acknowledge accepted operations. Persist through the platform store.

Partial checkpoints persist merged append-only history, accepted/rebased operations, the validated cursor and `syncHasMore`. They retain existing content and apply only tombstones reached in the ordered change stream. They do not import a latest snapshot whose omissions could remove a card before its historical reviews have been replayed. Subsequent invocations resume from the saved cursor and defer content/review uploads until the backlog is consumed. The final resumed checkpoint clears `syncHasMore`; another normal sync uploads local edits before hydrating server content. Both clients explicitly ask the learner to sync again while remote changes, deferred uploads or pending review batches remain. Failed validation/replay preserves the previous local checkpoint.

Transport deadlines, authentication and response-body bounds remain adapter responsibilities. Coordination receives explicit time and ID generation. A failed operation leaves pending work available for retry; remote and local writes cannot share a transaction.

## Review identities and ordering

Events have stable review IDs, card IDs, device IDs and device sequences. Requests include the causal base event, device/effective timestamps, rating, scheduler family/version and parameter-set identifier. Duplicate events converge by identity; ID or device-sequence collisions remain marked until repaired and successfully retried. Repairs preserve history and allocate new device sequence identity where necessary.

New application reviews also record `previousStateHash`: SHA-256 of the ordered tuple `["recall-fsrs-schedule-v1", due, stability, difficulty, elapsed_days, scheduled_days, learning_steps, reps, lapses, state, last_review]` before scheduling. Dates use canonical UTC ISO strings; missing/null `last_review` becomes null. Explicit time zones and finite numeric fields are required, so property order and ordinary JSON serialization do not change the digest. This is audit metadata; schedule replay remains based on append-only review history. `elapsedMs` accepts a caller-measured nonnegative safe integer or null; an absent measurement remains null. Sync preserves supplied hashes/durations, and imported or legacy null metadata stays null without fabricated measurements.

The sync core establishes deterministic causal order. Scheduler replay uses the recorded parameter set for each historical event. Unknown parameters produce a typed replay failure; clients preserve their current workspace instead of silently choosing different parameters. Schedules are derived state, while reviews remain append-only.

## Device clock policy

Timestamp boundaries validate actual Gregorian dates, hours, minutes, seconds and explicit offsets (at most ±14:00) and years 0001–9999 before parsing; impossible dates and invalid zones fail before writes. Effective timestamps are normalized to UTC at millisecond precision. Causal replay compares instants rather than timestamp text, so equivalent or differently offset timestamps have the same chronological ordering.

For each new review admission, the server injects its reception instant and derives `effectiveReviewedAt` from `reviewedAtDevice`: an older offline timestamp remains unchanged in time; a future device timestamp is clamped to reception. No clock offset or missing measurement is inferred. The original device timestamp remains separate evidence (storage may normalize its representation). The client-supplied effective timestamp remains in the version-1 request for compatibility, but does not choose a new server event's effective time. Existing accepted events keep their first effective timestamp on retries; duplicate checks compare immutable device-time and review metadata rather than a newly calculated reception time. Previously accepted history is not retroactively reclamped.

Every successful current server push returns `acceptedReviewEvents`, the canonical events for exactly its accepted IDs, including duplicate retries. The shared coordinator validates the exact unique accepted ID set and immutable metadata against the submitted batch before reconciliation. This receipt updates only derived `ratedAt`/`effectiveReviewedAt` values for an existing local event while retaining its original device evidence. Receipts are applied even when the pull cursor is already past that event; normal pull still carries first-admission events. Older servers without this optional response field retain the ordinary pull path. Neither a receipt nor conflict resolution replaces another event's immutable review history.

## Content and deletion

Offline deletion keeps a private `retainedReviewAreas` snapshot for removed cards whose reviews are still pending. These snapshots are excluded from the active library and portable publication exports; private backups retain them. Before each normal review push, the coordinator looks up at most 100 owner-scoped card identities through `/api/v1/workspace/review-identities`. Existing identities, including tombstoned cards and areas, accept history without being recreated. Missing identities require validated retained content; older workspaces without that evidence fail with `deleted-review-content-missing` and retain their outbox for private-backup recovery.

Accepting a server conflict preview also preserves private content for any removed local card with pending reviews. Only cards absent from the approved active preview receive the corresponding deletion intent; existing local deletion intents and retained snapshots survive acceptance. These cards stay out of the active library while the next sync can provision a missing identity, upload its history and confirm its tombstone. Cards kept by the preview are not tombstoned. If the server has already deleted an entire area and lacks a reviewed local card identity, the retained private snapshot remains available for backup recovery rather than silently recreating the deleted area.

Missing deleted cards are provisioned in the current review batch with their objective prerequisite closure. An affected area's active replacements wait until a later sync, except for missing live card identities referenced by the same current review batch. Those live cards are included with their objective prerequisites and provenance so a mixed deleted/live batch cannot submit reviews for unprovisioned identities. Other live additions remain deferred, keeping the staged document within the canonical 500-card and 200-objective limits. Once reviews are acknowledged, card tombstones remove the staged cards; an area tombstone waits until pending history has been accepted and uses the freshly acknowledged content hash. Whole-area deletions also tombstone accepted staged cards between batches to free room without restoring the local area. Hidden snapshots are released only after both review acknowledgment and the applicable confirmed tombstone. Partial pulls and edits/deletions made during a sync preserve the latest private evidence.

If existing remote content plus the next required retained batch cannot fit the canonical card/objective limits, synchronization fails explicitly with `deleted-review-provision-capacity`; it does not drop reviews or content. A private backup preserves the recovery evidence. Conflict approval alone does not increase those limits: the remote area's content or capacity must be reconciled before retrying. Optimistic hash checks and comparison with the exact submitted documents protect an area deletion from silently overwriting a concurrent remote edit.

Content hashes identify optimistic versions of portable area snapshots. Card and area deletion propagate as tombstones; content resurrection is rejected. A local area deletion retains reviews. An approved server-conflict load replaces content while retaining private reviews and reconciling schedules; it is not automatic last-write-wins.

Each invocation retains its immutable content baseline. Reconciliation compares it with the latest local workspace: area/card edits, additions and deletions made during network work stay local, and newly provisioned areas deleted in flight retain a deletion intent. Returned server hashes remain the acknowledged bases for later uploads. If an area changed differently both locally and remotely, the client retains local content and a private conflict marker; the next sync presents the server version for explicit approval before uploading. Clients disclose preserved pending edits. The native review and sync commit path reads the current workspace in a serialized lane and serializes local store writes, including conflict acceptance, so newer review history is retained. Native reset/account deletion increments an operation generation and blocks local commits during cleanup; stale sync results and server previews cannot restore an erased workspace. Native reset/deletion also drains and clears indexed pending publication/fork records (including publication share tokens), known legacy keys and tutor session links. Operation stores and tutor-link callbacks are bound to the UI generation, so stale callbacks cannot recreate erased credentials. Incomplete cleanup retains its targets and keeps writes paused for an explicit reset retry.

Portable snapshots and publications exclude personal review history, schedules, tutor observations and transcripts. Forked content starts an independent private history and uses the server-created identities/base hash on its first synchronization.

## Contracts and limits

Effect Schema owns request/response validation in `@recall/contracts`. Review pull pages contain at most 100 changes. The coordinator checks cursor progress and page validity and refuses malformed data. Server body limits and per-process request limits are documented in [HTTP operations](http-operations.md).

Runtime RLS, interrupted sync and concurrent device acceptance remain required before release. This document describes the implemented protocol; source compilation does not prove those runtime properties.
