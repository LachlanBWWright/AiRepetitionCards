# HTTP operations

The Next.js `observeRoute` wrapper and ASP.NET request-observation middleware attach a server-generated `x-request-id`, including expected errors and sanitized unexpected failures. ASP.NET catches unexpected handler exceptions and returns a private `{ error: "request-failed", requestId }` response unless the response has already started. Set `RECALL_HTTP_LOGGING=true` on the server to emit sanitized operation, status, duration and timestamp events; request bodies, identities, IPs, tokens, exception details and response bodies are excluded.

`GET /api/v1/auth/session` returns the versioned `AuthSessionResponse` contract: authenticated status, a display label and canonical account ID, without session credentials or external identity claims. It verifies the canonical account on the server and hides internal ChatGPT account aliases. Unauthenticated or unconfigured clients receive an anonymous status; authentication service failures return HTTP 502. Responses are private and non-cacheable. Browser account controls use this endpoint with HttpOnly session cookies. `POST /auth/sign-out` requires the same origin and signs out only the current application session.

Workspace sync and private-media clients send `x-recall-workspace-owner` with the canonical account ID verified for the operation. The shared authentication boundary validates this UUID and compares it with the authenticated subject before allowing repository or storage work. A malformed or mismatched value returns private HTTP 409 with `error: "workspace-account-changed"`. Electron forwards this one validated identity field through its fixed API proxy; bearer credentials remain in the main process. This check prevents an account change during an awaited request from directing earlier workspace content to the newly signed-in account.

`POST /api/v1/workspace/review-identities` accepts a v1 envelope with 1–100 unique canonical UUID card IDs in an 8 KiB JSON body. It returns only caller-owned card/area identities and whether the card or area is archived, including identities absent from the active workspace snapshot. Missing and inaccessible identities are omitted without distinguishing them. Ownership is checked through the authenticated client and an explicit owner-area filter. Responses include the verified account ID, use private/no-store caching and share the workspace request-rate bucket. Sync uses this lookup after its ownership checkpoint to avoid resurrecting archived content while delivering offline reviews.

## Optional operational logs

Set `RECALL_HTTP_LOGGING=true` on the server to write one JSON event per completed request. Logging is disabled by default. Events contain only the schema version, operation name, status, elapsed milliseconds, generated request ID, timestamp and unexpected-failure flag. They contain no account identifiers, IP addresses, URLs, query strings, tokens, prompts, content, response bodies, exception messages or stack traces. A logging failure does not change the API response.

Unexpected handler failures return a private, non-cacheable HTTP 500 response with `{ error: "request-failed", requestId }`. The operation event records that an unexpected failure occurred without exposing its cause. Expected failures retain the endpoint's established status and error payload. This opt-in log stream is operational evidence; external log collection, retention and alerting still require deployment configuration.

## Request abuse limits

`api-rate-limit.ts` checks verified account identity and operation scope before request-body parsing, repository work or provider calls. Review/workspace sync, tutor, account export/deletion, privacy controls, publication mutations and private-media routes consume these limits. The policy lives in the shared Effect application layer; server configuration selects Redis or memory storage. Account, media and publication mutations use separate subject namespaces so they do not consume the sync/tutor buckets. Public publication routes use an aggregate anonymous origin bucket plus optional keyed IP buckets from an explicitly trusted proxy.

| Shared scope             | Requests per 60-second window | Methods                                                                                    |
| ------------------------ | ----------------------------- | ------------------------------------------------------------------------------------------ |
| Review sync              | 120                           | Review push and pull together                                                              |
| Workspace sync           | 30                            | Workspace read, write and identity lookup                                                  |
| Tutor read               | 60                            | Read tutor session                                                                         |
| Tutor write              | 20                            | Tutor actions and proposal decisions together                                              |
| Account operations       | 30                            | Account export, deletion and tutor-history erasure together, separate account namespace    |
| Privacy policy read      | 60                            | Tutor privacy policy, separate account namespace                                           |
| Private media reads      | 120                           | Workspace media download, separate media-read namespace                                    |
| Private media writes     | 120                           | Workspace/publication media upload together, separate media-write namespace                |
| Publication mutations    | 30                            | Publish, fork and token rotation/revocation together, separate publication-write namespace |
| Public publication reads | 120 total per store           | Published snapshots, upstream updates and public/unlisted media together                   |

A denied private request receives HTTP 429 with `error: "rate-limited"`, `retryAfterSeconds` and a matching `Retry-After` header. Store/decision failures return HTTP 503 with `error: "rate-limit-unavailable"` and `Retry-After: 60`. Publication routes retain the versioned publication error envelope with `error: "publication-unavailable"` and the same status/retry headers. Rate-limit failures are private and non-cacheable even on public-read routes. AI usage quotas and payload/media limits remain separate protections. Area tombstones share the workspace-sync bucket.

503 bodies also carry `retryAfterSeconds: 60`. Shared tutor clients validate known limiter envelopes against their status and a bounded integer retry delay (1–60 seconds); malformed known responses fail validation. Web/native tutor recovery messages distinguish request throttling, temporary request unavailability and daily AI allowances. Retries are deliberate user actions, with no automatic resubmission; draft text, history and proposals remain available.

`API_RATE_LIMIT_MODE=redis` selects the shared REST Redis adapter. Set `API_RATE_LIMIT_STORE_REST_URL`, `API_RATE_LIMIT_STORE_REST_TOKEN` and a deployment-specific `API_RATE_LIMIT_STORE_PREFIX` (up to 64 ASCII letters/digits/colon/underscore/hyphen). Use an HTTPS endpoint compatible with [Upstash's Redis REST protocol](https://upstash.com/docs/redis/features/restapi). A single [Redis Lua script](https://redis.io/docs/latest/develop/programmability/eval-intro/) checks and increments a fixed-window counter atomically using Redis server time and expires its key. Keys hash the scoped subject; raw account IDs and IP addresses do not appear in stored keys or error responses. The ASP.NET API maps account operations and publication mutations onto `workspace-sync`, privacy reads onto `tutor-read`, and media plus public reads onto `review-sync`, while retaining separate subject namespaces. This preserves the corresponding Next.js counters during a staged cutover. HTTP responses are bounded to 4 KiB, redirects are rejected, and a 10-second deadline includes body consumption. Configuration, storage and response failures return 503 without falling back to memory.

Production defaults to Redis when mode is absent. `API_RATE_LIMIT_MODE=memory` explicitly selects the development/single-process adapter: at most 10,000 buckets, expired-bucket cleanup, fail-closed capacity handling and counters that reset on restart. Memory windows start with the first request; Redis windows align to Redis server time. Memory mode cannot prove global enforcement across instances. Development defaults to memory and permits loopback HTTP Redis endpoints; production Redis requires HTTPS. The checked-in `.env.example` selects memory for local development; change the mode and supply Redis credentials before a distributed deployment.

For IP limits, set both `API_RATE_LIMIT_TRUSTED_IP_HEADER` and `API_RATE_LIMIT_IP_HMAC_SECRET` (a random secret of at least 32 characters). Both blank disables IP buckets; partial configuration fails closed. The trusted header must contain exactly one IPv4 or IPv6 address, without a port, zone, bracket or forwarded chain. IPv6 spelling and IPv4-mapped IPv6 normalize to stable identities before HMAC hashing. Raw IPs exist only transiently in request processing; only a keyed digest enters the rate-limit store. Use the same secret on every instance; rotation starts new IP buckets.

Protected endpoints authenticate before rate limiting. Requests without a verified identity continue to endpoint authentication and do not consume IP or account buckets, preserving the endpoint's established authentication response. Once authenticated, configured trusted-IP limits run before the account bucket; invalid or partial trusted-IP configuration then fails closed with HTTP 503. Public publication reads are anonymous by design and always use the aggregate bucket, plus the optional trusted-IP bucket.

Enable this header only when the deployment proxy strips client-supplied values, overwrites the header from its verified connection peer, and prevents direct access to the origin. The application never automatically trusts `X-Forwarded-For` or another hosting header. Missing/malformed trusted values return 503 for requests that reach rate limiting. A verified IP bucket is checked before the account bucket with the same scope policy and separate namespaces; anonymous publication reads also retain their aggregate bucket. Requests can be denied by either limit. Redis counters and trusted-header behavior still require deployment acceptance; source and static builds do not prove the proxy's trust boundary.

The anonymous bucket is shared by all publication visitors using the store and can pause legitimate origin reads after a burst; cached publication responses keep their existing cache policy. Authentication/session/capability routes and the protected scheduled-retention endpoint remain outside these buckets. Deployment edge abuse protection and external spend alerts remain separate controls.

## Account identity cleanup

Account deletion removes linked OpenAI identity mappings before deleting the canonical account. A configured identity store remains eligible for cleanup even when provider sign-in is disabled. Partial store configuration or failed cleanup prevents canonical deletion and returns `account-deletion-cleanup-unavailable`; the authenticated user can retry. Store cleanup is idempotent and retried up to three attempts with a short backoff. If identity cleanup succeeds but canonical deletion fails, the account remains valid through its existing session or email sign-in; OpenAI identity linking may need to be performed again explicitly. No successful deletion acknowledgement is returned until both cleanup and canonical deletion have succeeded.
