# Publishing HTTP contracts

Publication endpoints live under `/api/v1`. Their JSON request and response schemas are owned by `@recall/contracts`; web, Electron and native clients use the shared Effect publishing client from `@recall/application`.

| Operation                              | Endpoint                                          | Success                                                                        |
| -------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------ |
| Publish an immutable area version      | `POST /api/v1/knowledge-areas`                    | 201 when created; 200 when replayed, version and optional unlisted share token |
| Read a reviewed version                | `GET /api/v1/published/:versionId`                | 200, version                                                                   |
| Check a fork's public upstream updates | `GET /api/v1/published/:versionId/updates`        | 200, known version identity and optional newer public version identity         |
| Fork a reviewed version                | `POST /api/v1/published/:versionId/fork`          | 200, saved document, area ID, content hash and source version                  |
| Rotate or revoke a share token         | `PATCH /api/v1/published/:versionId/token`        | 200, version ID and token or null                                              |
| Upload a referenced media asset        | `POST /api/v1/publishing/media/:mediaId`          | 200 or 201, validated reference                                                |
| Read a published media asset           | `GET /api/v1/published/:versionId/media/:mediaId` | 200, binary asset                                                              |

JSON publishing requests and success/error responses include the additive `schemaVersion: 1` discriminator. Legacy bodies that omit it remain accepted. An explicit unsupported version fails validation. Binary media responses retain their existing headers instead of a JSON envelope.

Fork requests additionally require an `operationId` UUID and responses echo it. The client stores the pending operation before sending the request and retains it after lost responses, attachment failures or unsuccessful local acceptance. Reusing the same owner/source/operation tuple derives the same area, objective, card and initial revision identities. The server recovers the owner's matching immutable initial snapshot before creation and after uncertain writes, validates its document, hash and lineage, and never restores a deleted copy. Recovery returns the original operation result without replacing later edits. Successful durable local acceptance clears the pending operation; another deliberate copy starts a new operation. This uses the existing snapshot storage and transaction RPC without a schema change.

Publishing also requires an `operationId`, echoed only by its authenticated mutation response. Web/native clients persist the operation, canonical request fingerprint, and (for unlisted publication) a securely generated 32-byte base64url `shareToken` before submitting. The server derives the version UUID from owner, source area and operation, recovers the owner-only immutable row before creation and after uncertain writes, and rejects changed content or metadata with `publication-operation-conflict` (409). Interrupted replies retain the pending attempt; successful response acknowledgment clears it. A changed draft offers an explicit new-attempt action because the earlier version may already exist. Public reads never expose the operation or capability hash.

Unlisted token recovery returns the saved client token only when its hash still matches the current stored hash. Replaying after token rotation or revocation recovers the version without returning an active token or regranting access. Tokens are validated for the documented format; shipped clients obtain their entropy from browser/Expo cryptographic random bytes. SecureStore indexes pending native records so reset/deletion can clear records even for incomplete forks. Web pending writes use the shared cross-tab erasure fence.

Independent publication operations still allocate human-readable version numbers through the existing latest-version read and unique constraint. Concurrent different attempts may receive `version-conflict`; retrying the same pending operation reads the newer number without changing its deterministic version UUID. This explicit retry remains necessary until version-number allocation becomes an atomic database operation. No schema or database changes are required for operation replay.

Publication and operation UUIDs are canonicalized to lowercase at validation, identity generation and pending-operation storage. Changing UUID letter case preserves the same fork operation and recovery result. Generic imported content identifiers and provenance `sourceId` values retain their original case.

Publication preparation retains inherited attribution/license and derives lineage from the portable content. A supplied envelope lineage that contradicts that content is rejected. Public/unlisted publication requires a license; unknown rights, imported/forked content or a changed license also require explicit `reuseConfirmed: true`. This is the publisher's acknowledgment, not an independent license verification. Private snapshots may keep unknown rights. Both the shared client and server validate these rules and normalize metadata consistently into the immutable content and publication envelope.

Failures retain `{ error }` and add `schemaVersion`; `PublishingErrorResponseSchema` enumerates the supported codes. Publishing errors and authenticated successes use private, non-cacheable responses. Public publication reads may be cached for 60 seconds; token-authorized reads are private and not stored. The client reports unknown or malformed error bodies as an HTTP failure with a null code, and never passes arbitrary vendor strings through as application error codes.

The shared client validates success payloads against the original request: version IDs must match reads and token changes, published content must belong to the requested area, fork IDs must agree with the document and its source lineage, and revoked tokens must be null. Legacy optional source-area and visibility fields remain optional. IDs, tokens, content hashes, ISO timestamps and portable documents are validated at the boundaries. Shape validation does not replace server-side authentication, content-hash verification or media-integrity checks.

## Upstream discovery

`PublishingApi.checkUpdates({ versionId, sourceAreaId?, shareToken? })` checks a fork's exact `forkedFromVersionId`. The versioned response contains `knownVersion: { id, version, sourceAreaId }` and either `latestPublicVersion: { id, version, sourceAreaId, createdAt }` or null. The client validates the requested baseline ID, any supplied source identity, candidate source equality, a distinct candidate ID and a strictly higher version number. Generic content provenance IDs retain their case; publication/source UUIDs are canonical.

The route first verifies access to the existing immutable version, including portable-content/hash validation. It resolves the publisher from that server-owned record or its exact unlisted capability, then queries only **public** newer versions with the same publisher and source-area identity. An optional client source assertion cannot choose a publisher or change the discovery anchor. Unreadable/malformed baselines receive the generic publication-not-found response; provider query failures return publication-unavailable (503), preserving retry rather than reporting no updates. Candidate content and hashes are validated before returning its identity.

The only query parameters are optional `sourceAreaId` and `token`, each occurring once; unknown or repeated parameters fail validation. Unlisted capabilities authorize their exact existing version and never discover newer unlisted/private existence, titles, counts, identities or content. A newer unlisted version needs its own explicit share link. Discovery responses are private and not cached, and contain no publisher identifier, token or capability hash.

Both clients present “new version available” with an explicit review action. Reviewing reads that exact public version and reuses the existing source-aware comparison and independent-copy approval flow. The current fork, private history and scheduling remain unchanged; no automatic merge is performed. Electron's narrow API allowlist admits the validated discovery request shape. Exact public reads ignore ordinary Supabase bearer credentials as share capabilities; explicit query capabilities continue to take precedence.
