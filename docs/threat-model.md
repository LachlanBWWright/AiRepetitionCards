# Security and privacy threat model

## System and sensitive data

Recall has three deployment boundaries: the Next.js web/API server, Supabase Auth/Postgres/Storage, and the OpenAI API. Browser, Expo, and Electron clients share domain contracts but keep local workspaces on-device (IndexedDB or SQLite). Electron keeps bearer credentials in its main process and uses OS encrypted storage; mobile uses SecureStore. The web server holds provider credentials. Supabase owner data includes learning content, append-only review events, tutor transcripts/observations, proposals, and AI usage. Published snapshots and their referenced media are intentionally shareable. Optional website ChatGPT identity uses durable atomic browser-bound OIDC transactions and explicit account linking; local desktop plan credentials remain encrypted in Electron main. Local private workspace backups include review history and schedules.

## Trust boundaries and controls

- **Client to API:** Treat all request bodies, imported archives, and learner-authored tutor instructions as untrusted. Route contracts validate payloads and bound selected request sizes. Authenticated JSON responses set `private, no-store` and vary on authorization and cookies so private learning data is not cached across users. Tutor requests require an authenticated account; database ownership is additionally enforced with RLS. Electron IPC validates sender, payloads, and allowed API routes. Web responses set no-sniff, anti-framing, referrer, and browser-permission headers; production responses also set HSTS.
- **API to Supabase:** Normal API reads and writes use the user's session so RLS applies. The account deletion route uses `SUPABASE_SERVICE_ROLE_KEY` only on the server and calls the service-role-only erasure function. Never expose this key to client bundles or logs.
- **Tutor to OpenAI:** The server sends the selected learning-area snapshot, tutor history, and current learner input to OpenAI. Treat these as disclosed to that provider. User content is delimited as data; the model has no database tools. Structured responses are validated and proposals require learner approval. A database-backed limit of 30 requests per account per UTC day, optional durable hosted admission budgets and provider token metering are implemented. Per-process API throttles limit individual instances; distributed request throttling and usage alerts remain deployment concerns.
- **Published content and media:** Public snapshots/media are accessible to anyone. Unlisted links are bearer secrets: only SHA-256 token hashes are stored, and revocation/rotation invalidates old links. Media downloads must match an immutable snapshot reference and pass MIME, length, and SHA-256 checks. A leaked unlisted URL grants access until revoked.
- **Local data:** Device access, malware, OS account compromise, and user-exported backups are outside server RLS. Protect desktop through OS account controls and mobile through device passcode/encryption. Treat private backup ZIPs as sensitive files.

## Main risks and remaining controls

| Risk                                 | Current control                                                                                          | Operational follow-up                                                                                                                             |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cross-account access                 | RLS and owner-scoped server queries                                                                      | Apply migrations and run real PostgreSQL/RLS tests before production; generated DB types are checked in, while live isolation remains unverified. |
| Credential or service-role leak      | Server-only environment variables; Electron main-process credential handling                             | Restrict secret access, rotate after suspected exposure, and scan deployment logs/configuration.                                                  |
| Malicious import or prompt injection | Bounded archive parsing, schema/hash validation, untrusted tutor context, no model tools                 | Keep hostile archive and prompt-injection cases in security review; inspect new import formats before release.                                    |
| Unintended publication               | Explicit publish/fork flow, immutable snapshots, unlisted token rotation/revocation                      | Explain public versus unlisted visibility clearly; revoke a link promptly if disclosed.                                                           |
| AI cost abuse                        | Daily account quota, durable optional admission budgets and provider metering                            | Add edge/API abuse throttling and usage alerts before broad public launch.                                                                        |
| Data loss or incomplete deletion     | Account erasure function deletes owner records before Auth identity; local cache cleanup is explicit     | Configure managed database backups and prove restore; deletion and backup-retention behavior need a production runbook and runtime validation.    |
| Client compromise                    | Electron sandbox/context isolation and narrow IPC; encrypted desktop session storage; mobile SecureStore | Validate packaged builds and auth/media flows on supported OS/device versions.                                                                    |

## Incident response

For leaked credentials, revoke/rotate the affected Supabase or OpenAI secret, redeploy, and review provider/database access logs for the exposure window. For a leaked unlisted share, rotate or revoke its token and assess whether the snapshot should be unpublished; already downloaded copies cannot be recalled. For suspected owner-data exposure, preserve relevant logs, disable the affected route or credential, identify impacted accounts and data, and follow the deployment operator's notification obligations. Do not place tokens, private tutor content, or full request bodies in diagnostics. Opt-in HTTP operation logs contain only sanitized request metadata. Tutor history can be erased separately from study data; configure inactive-session retention and the protected cleanup scheduler as documented in `tutor-privacy.md`.

This is an implementation-grounded working model, not a completed security assessment. Production RLS integration checks, general abuse throttling, backup/restore drills, and cross-platform release validation remain open.

Web CSP uses per-request script nonces and dynamic rendering. It restricts script/connect/frame/object/form/base capabilities while allowing existing inline CSS and Wasm compilation; development alone allows JavaScript evaluation. Do not cache nonce HTML across requests. Browser enforcement remains unverified.
